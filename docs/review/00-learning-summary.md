# Agent 学习指南：精炼版（面试向）

> 用途：作为 GEO2 11 维度锐评（`01-...md` 到 `11-...md`）的方法论依据与"达标线"参考。

---

## 1. 核心公式

```
Agent = Model + Harness
```

Harness（驭缰）包含除模型本身之外的**全部**代码、配置与执行逻辑：

- 系统提示 / 系统消息
- 工具 / 技能 / MCP
- 沙箱 / 文件系统 / 浏览器等基础设施
- 编排逻辑（Agent Loop）
- 钩子 / 中间件（用于确定性执行）

**核心理念**：Humans steer, agents execute.（人类掌舵，智能体执行。）

---

## 2. 关键链路（Agent Loop）

```
用户输入 → 模型判断 → 工具调用 → 工具结果返回 → 模型继续推理 → 状态保存
```

七个关键问题（任何 Agent 项目必须能回答）：

1. 用户输入后，系统状态如何变化？
2. 模型何时继续生成，何时停下来等工具返回？
3. 工具如何注册、调用、返回？
4. 工具调用失败后，系统如何处理？
5. 上下文过长时，如何裁剪？
6. 哪些操作需要用户确认？
7. 会话结果如何保存和恢复？

---

## 3. 工程分层

| 层级 | 职责 | 常用技术 |
| --- | --- | --- |
| API 服务层 | 对外提供 REST/WS 接口 | FastAPI / Hono |
| 会话管理 | 多轮对话状态、上下文维护 | Redis / DB |
| Agent 运行时 | Loop 控制、工具注册、权限 | LangGraph / 自研 |
| 工具层 | 工具定义、调用、结果校验 | MCP / Function Call |
| 上下文工程 | 记忆管理、裁剪策略、RAG | 向量库 / 摘要 |
| 观测层 | 日志、追踪、成本统计 | Langfuse / Sentry |
| 评测层 | 自动化评测、回归测试 | 自建评测集 |

---

## 4. 严格分层架构（OpenAI 范式）

```
Types → Config → Repo → Service → Runtime → UI
```

横切关注点（认证、连接器、遥测、功能开关）只能通过显式接口 `Providers` 访问。所有其他依赖由自定义 lint + 结构测试**机械式阻断**。

**核心洞察**：规则靠工具强制执行，不靠文档提醒。

## 5. Harness Engineering 六大核心概念

| # | 概念 | 一句话 |
| --- | --- | --- |
| 1 | 仓库即记录系统 | 不在仓库里的东西对智能体不存在 |
| 2 | 地图非手册 | AGENTS.md 是 ~100 行索引，不是百科全书 |
| 3 | 机械化执行 | lint + CI 结构测试机械执行架构约束 |
| 4 | Agent 可读性 | 优先为智能体推理能力优化代码文档 |
| 5 | 吞吐量改变合并理念 | 修正优于阻塞（纠错成本低，等待成本高） |
| 6 | 熵管理 | 技术债持续小增量偿还（GC 式清理） |

## 6. 11 维度的判断标准

> 下面 11 个小节一一对应 `01-...md` 到 `11-...md`，作为各锐评文件 §1 维度定义的方法论依据。

### 6.1 Agent Loop（参考：`01-agent-loop.md`）

- **定义**：用户输入到最终输出全链路的清晰度与可追溯性。
- **达标线（3 分）**：链路完整、有状态保存、最大轮次限制、上下文裁剪。
- **良好（4 分）**：错误注入可控、Loop 可视化、断点续跑。
- **卓越（5 分）**：Loop 抽取可复现、可回放、每次运行有审计轨迹。

### 6.2 工具边界（参考：`02-tool-boundary.md`）

- **定义**：工具的参数/返回值/失败模式/调用权限边界是否清晰。
- **达标线**：每个工具有 schema、错误返回值、不破坏 Agent Loop。
- **良好**：工具可独立测试、文档完整、有降级策略。
- **卓越**：工具描述对 LLM 友好、有评测覆盖。

### 6.3 上下文可控（参考：`03-context-control.md`）

- **定义**：上下文窗口管理、压缩、检索的工程能力。
- **达标线**：有最大 token 限制、有超限裁剪策略。
- **良好**：滑动窗口 + 历史摘要 + 工具结果截断。
- **卓越**：自适应压缩、可解释裁剪决策。

### 6.4 权限策略（参考：`04-permission.md`）

- **定义**：高风险操作的鉴权、确认流、审计。
- **达标线**：危险工具有用户确认。
- **良好**：权限分级、有审计日志。
- **卓越**：策略可声明式配置、有自动化测试覆盖。

### 6.5 失败恢复（参考：`05-failure-recovery.md`）

- **定义**：工具失败、超时、网络错误的降级与重试。
- **达标线**：有 try/except + 重试。
- **良好**：有降级回答模板、有故障注入测试。
- **卓越**：可重放、可恢复会话。

### 6.6 评测体系（参考：`06-evaluation.md`）

- **定义**：自动化评测 Agent 输出质量的能力。
- **达标线**：≥30 条评测用例、覆盖 5 类场景。
- **良好**：失败原因分类、可回归。
- **卓越**：与 CI 集成、人评结合。

### 6.7 可观测性（参考：`07-observability.md`）

- **定义**：日志、追踪、成本统计的完整度。
- **达标线**：全链路日志、有 token 成本统计。
- **良好**：有 tracing、错误聚合、可视化面板。
- **卓越**：可回放、可重跑。

### 6.8 HITL（参考：`08-hitl.md`）

- **定义**：Human-in-the-loop 关键节点的确认流。
- **达标线**：高风险操作有确认。
- **良好**：确认流可中断可继续。
- **卓越**：可配置策略、有用户反馈回路。

### 6.9 成本/延迟（参考：`09-cost-latency.md`）

- **定义**：Token 成本与延迟的可见性与控制。
- **达标线**：每次调用记录 token + 延迟。
- **良好**：有成本/延迟告警阈值。
- **卓越**：自适应模型选择、可解释成本结构。

### 6.10 架构分层（参考：`10-architecture-layering.md`）

- **定义**：Types → Config → Repo → Service → Runtime → UI 的严格分层。
- **达标线**：层间依赖方向正确、跨层有显式接口。
- **良好**：横切关注点（认证、遥测）通过 Provider 抽象。
- **卓越**：lint + 结构测试机械执行分层约束。

### 6.11 Harness 范式符合度（参考：`11-harness-engineering.md`）

- **定义**：项目整体对 Harness Engineering 范式的符合度。
- **达标线**：决策与规范版本化在仓库、有 AGENTS.md 索引。
- **良好**：架构约束由 lint/CI 机械执行、有评测体系。
- **卓越**：吞吐量为优先、有熵管理机制、分离构建/评判智能体。

## 7. 评测集设计模板

30–50 条覆盖：

| 类型 | 数量 | 示例 |
| --- | --- | --- |
| 正常问题 | 15 | 直接的、信息充足的问题 |
| 边界问题 | 8 | 模糊的、不完整的问题 |
| 数据缺失 | 8 | Agent 查不到数据的情况 |
| 诱导错误 | 8 | 试图让 Agent 越权或犯错 |
| 拒答 | 5 | 超出范围或敏感问题 |

**评测维度**：准确性 / 完整性 / 相关性 / 可执行性 / 幻觉率

**失败原因分类**（比"成功率"更重要）：

- 工具描述不清楚，模型选错了工具
- 上下文过长或缺失关键信息
- 模型误判用户意图
- 业务规则没有定义清楚
- 工具返回结果不稳定

## 8. 简历表达样例

❌ 不建议：

> "基于大模型实现智能问答系统"

✅ 建议改成：

> - 设计 Agent Loop，支持工具调用、会话状态保存、上下文动态裁剪
> - 接入 N 个领域工具（行情、估值、新闻、持仓），工具失败时有降级兜底策略
> - 为高风险操作（下单、删除数据）增加用户确认流程（Human-in-the-loop）
> - 构建 50 条评测集，覆盖正常/边界/数据缺失/诱导错误场景
> - 接入 Langfuse 进行全链路追踪，Token 成本降低 30%
> - 记录失败类型分布，并根据结果迭代优化工具说明和上下文策略

**好项目描述应说明**：做了哪些工程设计，解决了哪些边界问题，如何验证效果。

## 9. 好 Agent 项目的判断清单

- [ ] 是否解决真实业务问题？
- [ ] Agent Loop 是否清楚？
- [ ] 工具边界是否明确？
- [ ] 上下文是否可控？
- [ ] 权限策略是否完整？
- [ ] 失败后是否能恢复？
- [ ] 是否有数据持久化和会话管理？
- [ ] 是否有可观测性和日志追踪？
- [ ] 是否有评测体系？
- [ ] 是否有人机协同机制（Human-in-the-loop）？
- [ ] Token 成本和延迟是否被记录？
- [ ] 能否解释为什么选择这个架构？
